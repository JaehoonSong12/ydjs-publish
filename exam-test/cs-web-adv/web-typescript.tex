\question[4]
TRUE or FALSE: TypeScript is a superset of JavaScript, meaning all valid JavaScript code is also valid TypeScript code.
\begin{choices}
  \CorrectChoice TRUE
  \choice FALSE
\end{choices}
\begin{solution}
  TypeScript builds on JavaScript syntax and runtime behavior. Existing \texttt{.js} files can often be renamed to \texttt{.ts} and adopted gradually as types are added. A few edge cases exist (for example very old or non-standard syntax), but the superset relationship is the guiding model for migration.
\begin{lstlisting}[style=js]
// Valid JavaScript is valid TypeScript (types optional)
function greet(name) {
  return 'Hello, ' + name;
}
\end{lstlisting}
\end{solution}

\question[4]
TRUE or FALSE: Browsers run TypeScript source files directly without a compile step in typical production apps.
\begin{choices}
  \choice TRUE
  \CorrectChoice FALSE
\end{choices}
\begin{solution}
  Browsers execute JavaScript, not TypeScript. The compiler (\lstinline[style=bashinline]|tsc|) or a bundler (Vite, Webpack, esbuild) strips types and emits \texttt{.js}. Types exist for developers and the checker---they are erased before runtime.
\begin{lstlisting}[style=bash]
npx tsc greet.ts    # produces greet.js for the browser
\end{lstlisting}
\end{solution}

\question[4]
When TypeScript reports a \textbf{type error}, that usually means:
\begin{choices}
  \choice The browser will show the same error to every user at runtime
  \CorrectChoice The program failed static analysis before run---fix the source or adjust types before shipping
  \choice \texttt{npm} is not installed
  \choice The DOM is missing a router outlet
\end{choices}
\begin{solution}
  JavaScript often throws type-related bugs only when a branch runs (\lstinline[style=jsinline]|undefined is not a function|). TypeScript catches many of those during \lstinline[style=bashinline]|tsc| or IDE checks. Runtime logic errors still require tests and debugging.
\begin{lstlisting}[style=ts]
let id: string = 'a1';
id = 99; // compile error: number is not assignable to string
\end{lstlisting}
\end{solution}

\question[6]
What is \textbf{type hinting} (type annotation) in TypeScript? Explain its purpose and show how to hint a variable and a function's parameters and return type.
\begin{solutionorbox}[4.5in]
\textbf{Definition:} Type hinting is the practice of explicitly declaring the data type of a variable, function parameter, or return value using a colon (\lstinline[style=tsinline]|:|) followed by a type name.

\textbf{Purpose:}
\begin{itemize}
  \item \textbf{IDE support} --- autocomplete, parameter hints, inline documentation
  \item \textbf{Early bug detection} --- \lstinline[style=bashinline]|tsc| flags mismatches before runtime
  \item \textbf{Self-documenting code} --- contracts are visible to the next developer
\end{itemize}

\textbf{Examples:}
\begin{lstlisting}[style=ts]
const username: string = 'Jaehoon';

function calculateTotal(price: number, tax: number): number {
  return price + tax;
}
\end{lstlisting}

\textbf{Note:} Type hints are compile-time only; they are erased when TypeScript emits JavaScript.
\end{solutionorbox}

\question[6]
How do you type-hint a \textbf{string array} in TypeScript? Show variable declarations, use in a function, and a readonly form.
\begin{solutionorbox}[4in]
\textbf{Two equivalent syntaxes} (shorthand is most common):
\begin{lstlisting}[style=ts]
const skills: string[] = ['Java', 'TypeScript', 'Python'];
const tools: Array<string> = ['Docker', 'Kubernetes', 'Git'];
\end{lstlisting}

\textbf{In functions} (parameter and return type):
\begin{lstlisting}[style=ts]
function uppercaseAll(items: string[]): string[] {
  return items.map(item => item.toUpperCase());
}
\end{lstlisting}

\textbf{Read-only array} (prevents \lstinline[style=tsinline]|.push()| and \lstinline[style=tsinline]|.pop()|):
\begin{lstlisting}[style=ts]
const constants: readonly string[] = ['localhost', '127.0.0.1'];
\end{lstlisting}
\end{solutionorbox}

\question[4]
TRUE or FALSE: In TypeScript, the \lstinline[style=tsinline]|number| type represents both integers and floating-point values.
\begin{choices}
  \CorrectChoice TRUE
  \choice FALSE
\end{choices}
\begin{solution}
  TypeScript follows JavaScript's IEEE-754 model: there is no separate \lstinline[style=tsinline]|int| or \lstinline[style=tsinline]|float| keyword. \lstinline[style=tsinline]|number| covers whole numbers, fractions, \lstinline[style=tsinline]|NaN|, and \lstinline[style=tsinline]|Infinity|. Very large integers may use \lstinline[style=tsinline]|bigint| (\lstinline[style=tsinline]|100n|).
\begin{lstlisting}[style=ts]
let count: number = 42;
let ratio: number = 3.14;
let invalid: number = NaN;
\end{lstlisting}
\end{solution}

\question[4]
TRUE or FALSE: A union type allows a variable to hold one of several types, written with the \lstinline[style=tsinline]!|! symbol.
\begin{choices}
  \CorrectChoice TRUE
  \choice FALSE
\end{choices}
\begin{solution}
  Union types combine alternatives with the pipe (\lstinline[style=tsinline]!|!) operator. The value must be assignable to at least one member of the union; narrowing (\lstinline[style=tsinline]|typeof|, \lstinline[style=tsinline]|instanceof|, type guards) is required before calling type-specific methods.
\begin{lstlisting}[style=ts]
let id: string | number;
id = 'a1';
id = 99;
// id.toFixed();  // error until narrowed with typeof id === 'number'
\end{lstlisting}
\end{solution}

\question[4]
Which statement \textbf{narrows} a union \lstinline[style=tsinline]|string | number| safely?
\begin{choices}
  \choice Call \lstinline[style=tsinline]|value.toFixed()| without checking
  \CorrectChoice \lstinline[style=tsinline]|if (typeof value === 'number') { value.toFixed(2); }|
  \choice Assign \lstinline[style=tsinline]|value = null| to widen the union
  \choice Cast with \lstinline[style=tsinline]|as any| in every branch
\end{choices}
\begin{solution}
  \textbf{typeof}, \textbf{instanceof}, \textbf{in}, and user-defined \textbf{type predicates} (\lstinline[style=tsinline]|value is Fish|) tell the checker which branch is active. Until narrowed, only members common to all union parts are allowed.
\begin{lstlisting}[style=ts]
function format(value: string | number): string {
  if (typeof value === 'number') {
    return value.toFixed(2);
  }
  return value.toUpperCase();
}
\end{lstlisting}
\end{solution}

\question[4]
Literal types such as \lstinline[style=tsinline]|'success' | 'error'| are useful because they:
\begin{choices}
  \choice Force every string at runtime to be exactly six characters
  \CorrectChoice Restrict a value to specific string constants for safer APIs and exhaustiveness checking
  \choice Replace interfaces entirely
  \choice Compile to SQL \texttt{ENUM} columns automatically
\end{choices}
\begin{solution}
  Literal unions model fixed domains (status codes, alignment, HTTP methods). They pair with \lstinline[style=tsinline]|switch| and \lstinline[style=tsinline]|never| for exhaustiveness when the union grows later.
\begin{lstlisting}[style=ts]
type Status = 'loading' | 'ready' | 'error';
function setStatus(s: Status) { /* ... */ }
setStatus('ready');   // OK
setStatus('pending'); // compile error
\end{lstlisting}
\end{solution}

\question[4]

\begin{choices}
  \choice TRUE
  \CorrectChoice FALSE
\end{choices}
\begin{solution}
  A \textbf{tuple} fixes both \emph{length} and \emph{position} of each element's type. It is not a growable heterogeneous array. \lstinline[style=tsinline]|string[]| or \lstinline[style=tsinline]|Array<string | number>| model variable-length collections.

let user: [string, number] = ['Ada', 42];

// user = ['Ada'];   // compile error: missing second element
\end{lstlisting}
\end{solution}

\question[4]
TRUE or FALSE: If a variable is declared with type inference (\lstinline[style=tsinline]|let x = 10|), a string can later be assigned without a compile error.
\begin{choices}
  \choice TRUE
  \CorrectChoice FALSE
\end{choices}
\begin{solution}
  Inference locks the binding to the deduced type (\lstinline[style=tsinline]|number| here). Reassigning \lstinline[style=tsinline]|x = 'hello'| fails with \emph{Type 'string' is not assignable to type 'number'}. To allow both, annotate a union explicitly.
\begin{lstlisting}[style=ts]
let x = 10;
x = 'hello'; // compile error

let y: string | number = 10;
y = 'hello'; // valid
\end{lstlisting}
\end{solution}

let value: unknown = JSON.parse('{"ok":true}');

if (typeof value === 'object' && value && 'ok' in value) {
  // narrowed safely
}
\end{lstlisting}
\end{solution}

\question[6]
How do you create \textbf{arrow functions} in TypeScript? Show typed parameters, an implicit return, a \lstinline[style=tsinline]|void| handler, and a function type alias used with an arrow function.
\begin{solutionorbox}[4.75in]
\textbf{Syntax:} Arrow functions use \lstinline[style=tsinline]|() => {}| like JavaScript, with optional type annotations on parameters and the return type.

\textbf{Examples:}
\begin{lstlisting}[style=ts]
const add = (a: number, b: number): number => {
  return a + b;
};

const multiply = (a: number, b: number) => a * b;

const logMessage = (message: string): void => {
  console.log('Log: ' + message);
};

type MathOperation = (x: number, y: number) => number;
const subtract: MathOperation = (x, y) => x - y;
\end{lstlisting}

\textbf{Use cases:} Callbacks, array methods (\lstinline[style=tsinline]|map|, \lstinline[style=tsinline]|filter|), and short handlers where lexical \lstinline[style=tsinline]|this| binding is preferred over traditional \lstinline[style=tsinline]|function| expressions.
\end{solutionorbox}

\begin{choices}

let raw = '123';

\question[6]
What is \textbf{interface type hinting} in TypeScript? Show a basic object blueprint, use in a function parameter, and optional or \lstinline[style=tsinline]|readonly| properties.
\begin{solutionorbox}[5in]
\textbf{Definition:} An \textbf{interface} defines a structured blueprint for objects. Using the interface name as a type hint ensures variables and parameters have the expected property names and types.

\textbf{Purpose:} Interfaces act as compile-time contracts (for example matching API payloads), support \lstinline[style=tsinline]|extends| for hierarchies, and power IDE IntelliSense.

\textbf{Examples:}
\begin{lstlisting}[style=ts]
interface User {
  id: number;
  username: string;
  email: string;
}

const account: User = {
  id: 101,
  username: 'jsong',
  email: 'jaehoon@example.com',
};

interface Vehicle {
  make: string;
  model: string;
  year: number;
}

function displayVehicleInfo(car: Vehicle): void {
  console.log(`Driving a ${car.year} ${car.make} ${car.model}`);
}

interface Developer {
  readonly id: number;
  name: string;
  primaryLanguage: string;
  gitHubUrl?: string;  // optional
}
\end{lstlisting}

\textbf{Note:} Missing required properties or wrong types produce compile errors before the app runs. Interfaces are erased in emitted JavaScript.
\end{solutionorbox}

\question[4]
What is a main difference between a \lstinline[style=tsinline]|type| alias and an \lstinline[style=tsinline]|interface|? \emph{Select all that apply.}
\begin{checkboxes}
  \CorrectChoice Interfaces support declaration merging; type aliases do not
  \choice Type aliases work only in browsers; interfaces work only in Node.js
  \choice Interfaces can describe only primitives; types describe only objects
  \choice Type aliases cannot represent union types, but interfaces can
\end{checkboxes}
\begin{solution}
  Declaring two interfaces with the same name in one scope \textbf{merges} their members. A duplicate \lstinline[style=tsinline]|type| name is a compile error. Both constructs are erased at compile time (no runtime presence in either browsers or Node.js). \textbf{Type aliases} can express unions and tuples; interfaces describe object shapes and support \lstinline[style=tsinline]|extends|.
\begin{lstlisting}[style=ts]
interface User { name: string; }
interface User { age: number; }
// Merged: User requires name and age

type Status = 'idle' | 'loading' | 'done';  // union via type alias
\end{lstlisting}
\end{solution}

\end{choices}
\begin{solution}
  Merging is useful for extending third-party or global types without editing library source. Each declaration contributes properties to one merged interface.
\begin{lstlisting}[style=ts]
interface Window {

\question[6]
Are TypeScript \textbf{interfaces} meant only for plain objects? Contrast with Java interfaces and note when to prefer an interface versus a \textbf{type alias}.
\begin{solutionorbox}[5.25in]
\textbf{Short answer:} In TypeScript, interfaces primarily describe \textbf{object shapes} (including callable function objects and class contracts). They are erased at compile time and do not exist at runtime.

\textbf{Java vs.\ TypeScript:}
\begin{itemize}
  \item \textbf{Java} --- nominal typing: a class must \lstinline[style=javainline]|implements MyInterface| to satisfy the contract; interfaces often define behavior (methods).
  \item \textbf{TypeScript} --- structural typing: any value with matching properties satisfies the interface without an explicit \lstinline[style=tsinline]|implements| clause (though classes may still \lstinline[style=tsinline]|implements| for clarity).
\end{itemize}

\textbf{Beyond key--value objects:}
\begin{lstlisting}[style=ts]
interface MathTask {
  (x: number, y: number): number;
}
const divide: MathTask = (x, y) => x / y;

interface Lifecycle {
  onInit(): void;
}
class DashboardComponent implements Lifecycle {
  onInit() { console.log('Component loaded!'); }
}
\end{lstlisting}

\textbf{Interface vs.\ type alias:} Prefer an \textbf{interface} for extendable object models and API shapes. Prefer a \textbf{type alias} for unions (\lstinline[style=tsinline]|'idle' | 'done'|), tuples, primitives, or mapped types that interfaces cannot express.
\end{solutionorbox}

\question[4]

\begin{choices}
  \CorrectChoice TRUE
  \choice FALSE
\end{choices}

function greet(firstName: string, lastName?: string) {

// function bad(lastName?: string, firstName: string) {} // compile error
\end{lstlisting}
\end{solution}

\question[4]
A \textbf{rest parameter} collecting extra arguments uses:
\begin{choices}
  \choice \lstinline[style=tsinline]|function sum(a, b, c)|
  \CorrectChoice \lstinline[style=tsinline]|function sum(...nums: number[])|
  \choice \lstinline[style=tsinline]|function sum[number]|
  \choice \lstinline[style=tsinline]|function sum?: number[]|
\end{choices}
\begin{solution}
  The rest parameter must be last in the parameter list. It gathers remaining arguments into an array (or tuple when positions are fixed).
\begin{lstlisting}[style=ts]
function sum(...nums: number[]): number {
  return nums.reduce((a, b) => a + b, 0);
}

\question[4]
To access \lstinline[style=tsinline]|arg.length| in a generic function, which constraint is used?
\begin{choices}
  \choice Unconstrained \lstinline[style=tsinline]|<Type>| because every type has \lstinline[style=tsinline]|length|
  \CorrectChoice \lstinline[style=tsinline]|<Type extends Lengthwise>| where \lstinline[style=tsinline]|Lengthwise| requires \lstinline[style=tsinline]|length: number|
  \choice \lstinline[style=tsinline]|any| only, with no interface
  \choice A SQL \texttt{JOIN}
\end{choices}
\begin{solution}
  Unconstrained \lstinline[style=tsinline]|<Type>| cannot access \lstinline[style=tsinline]|length|. A constraint tells the checker which members are guaranteed.
\begin{lstlisting}[style=ts]
interface Lengthwise { length: number; }
function loggingIdentity<T extends Lengthwise>(arg: T): T {
  console.log(arg.length);
  return arg;
}
loggingIdentity('hello');              // OK: string has length
loggingIdentity(3);                    // error: number has no length
\end{lstlisting}
\end{solution}

\question[4]
A generic function \lstinline[style=tsinline]|function first<T>(items: T[]): T | undefined|:
\begin{choices}
  \choice Requires \lstinline[style=tsinline]|T| to be \lstinline[style=tsinline]|string| only
  \CorrectChoice Returns the same element type as the array elements (or \lstinline[style=tsinline]|undefined| if empty)
  \choice Returns \lstinline[style=tsinline]|any| always
  \choice Cannot accept empty arrays at compile time
\end{choices}
\begin{solution}
  One type parameter keeps input and output related: \lstinline[style=tsinline]|first([1, 2, 3])| is \lstinline[style=tsinline]|number | undefined|; \lstinline[style=tsinline]|first(['a'])| is \lstinline[style=tsinline]|string | undefined|.
\begin{lstlisting}[style=ts]
function first<T>(items: T[]): T | undefined {
  return items[0];
}
const n = first([1, 2, 3]);   // number | undefined
const s = first(['a', 'b']);  // string | undefined
\end{lstlisting}
\end{solution}
